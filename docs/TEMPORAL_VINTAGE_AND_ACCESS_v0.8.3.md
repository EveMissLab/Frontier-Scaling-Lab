# FSL v0.8.3｜跨世代 AI 功能性成本研究：時間座標與證據版本鎖定

**文件日期：2026-11-07（Asia/Taipei，UTC+08:00）**  
**正式來源：UTF-8 Markdown（唯一數學 delimiter：$...$ 與 $$...$$）**  
**原創文件與程式授權：Apache-2.0；外部資料保留原授權**  
**狀態：具可重算程式碼、真實官方發布日期來源及合成任務時鐘；尚未證實任何模型完成 24–48 小時自主任務**

## 0. 為什麼時間是不可省略的實驗變數？

若將某個 2026 年模型的任務完成率、API 定價、訂閱額度或新式 Agent 工具直接套回 2024 年，會發生嚴重的前視偏差（look-ahead bias）。

使用者提出的研究目標是：比較同一時期前沿與非前沿 AI 的功能性成果與實際成本，以及回推不同年份的 AI 在**當年的模型、工具、額度、使用者授權和市場價值條件下**，究竟能否完成同一任務，或需要付出多少代價。

因此，不能只在報告標題註明年份。每一筆可追溯的數據都必須有時間來源與精度。

## 1. 研究採取四條互不等同的時間軸

| 時間欄位 | 意義 | 不能被誰替代 |
|---|---|---|
| 事件／生效日期（event_effective_on） | 模型公開、價格生效、工具推出、服務停止等事實在何時發生 | 不能以資料擷取日替代 |
| 原始發布日期（published_on） | 來源網站／提供者何時公開這項主張 | 不能以原事件發生時間推定 |
| 本研究首次取得日期（first_captured_on） | FSL 觀測者何時實際擁有／讀到這筆資訊 | 不能倒填為原始發布日 |
| 真實任務的 UTC 時刻 | 目標凍結、Agent 開始、進展、完成、使用者接受、證據收集的精確時間 | 不能把日期精度硬轉成虛構秒數 |

前面三項主要使用發布者的日曆日期（YYYY-MM-DD），精度只有一天；當來源沒有公開發表的時分秒與時區時，不能自行宣稱當天 00:00 UTC 發生。

任務執行才要求附時區的 ISO-8601 時刻，例如本地 2026-11-04T00:00:00+08:00，等於 UTC 2026-11-03T16:00:00+00:00。這兩種顯示都必須保留，而不是只留下經轉換後的日曆日期。

**來源日期以 Asia/Taipei 的研究審閱日曆記錄；官方發布日仍只代表發行者的日曆日。** 同一天內的先後順序未知時，輸出會標示日內精度不確定。

## 2. 禁止資料倒流：兩種歷史模式

在給定評估截止日 $t$，定義來源 $i$ 的生效日期 $e_i$、原始公開日期 $p_i$、FSL 首次收集日期 $c_i$。

對先前真正發布的預測，其所使用來源必須滿足：

$$
e_i\le t,\qquad p_i\le t,\qquad c_i\le t.
$$

這是嚴格的 strict_known_at_time 模式。不符合的來源，不能因為今天查得到歷史網頁就回填成舊預測當年「已知」的證據。

反過來，retrospective_reconstruction 可研究當時已公開的資料，即使本研究現在才取得。它有歷史研究價值，但必須標註「事後重建」，**不能拿來宣稱 2024 年的研究者真的在當時發出了正確預測**。

即使來源在 2024 年公開過，也需另外判斷它當時是價格、可用性、預測還是模型宣傳，而不能將宣傳文當作獨立完成測試。

## 4. 實際任務的時間契約

每一個被拿來比較的真實任務嘗試，至少需要：

- 事前固定的使用者目標與任務契約 SHA-256，及目標凍結時刻；
- 確切模型、版本、服務提供者、當時的訂閱／API 路線及 Runtime manifest SHA-256；
- execution_started_at：實際開始執行時刻，帶 UTC offset；
- last_progress_at：目前最後可查證進展時刻（可以為 null，但未完成的截尾任務必須能記錄進展）；
- execution_finished_at：完成時刻，尚未完成則 null；
- accepted_at：獨立驗收時刻，不能早於完成；未驗收則 null；
- captured_at：觀測器正式取得證據的時刻，不能早於已寫入的未來事件；
- model_first_available_on、pricing_effective_on、price_first_captured_on：不能以更晚發布的模型或費率解釋先前的任務。

完成的日曆時間不等於有效自主工作時間；通過品質驗收時間也不等於 AI 真正完成其核心程式或數學推導的時刻。

對時間跨度，使用明確的 UTC 時刻差：

$$
T_{\mathrm{run}}=
t_{\mathrm{execution\ finished}}-t_{\mathrm{execution\ started}}.
$$

若未完成，時間跨度保持 null；不能因為「已經過了 48 小時」自動輸出某個模型具備 48 小時連續自主能力。

## 5. 對每個同期比較嘗試建立 time spine

v0.8.2 已能描述同一時期不同 AI 的訂閱、API、重試與已報告完成成本。v0.8.3 進一步要求每一個接受、失敗、未結案嘗試都有時間紀錄。

新的 time-anchored panel 會執行：

1. 所有嘗試必須一對一連結到時鐘紀錄，不能只給成功任務時戳、隱藏失敗任務。
2. task SHA、模型版本、Runtime manifest、提供者與 API／訂閱路線必須與比較組相同。
3. 不能使用研究截止時刻之後才取得的結果、評審或來源。
4. 模型推出或計價生效之後才能作為該次執行的當時條件。
5. 已報告接受的成果，以驗收時刻的台灣日曆日期登記；失敗以結束時刻、未結案以最後進展時刻登記。跨月任務不能錯置到開始月份。
6. 歷史費率若是在任務開始後才收集，允許標示事後重建，但不可宣稱任務開始時研究者已掌握它。
7. 真實觀測需要擷取時間不得在研究截止時刻之後；每份結果仍標示「尚未獨立認證長期自主工作」。

**這是資料時序與條件一致性檢查，不是驗證任務品質或 Agent 主體性的工具。**

## 6. 合成工程反例

test fixture：tests/fixtures/mission_clock_synthetic_2026-11-07.json。

其中有一個完全虛構的跨日執行：

- 2026-11-04 00:00（台灣）開始；
- 2026-11-05 23:30（台灣）結束；
- 執行跨度 **47.5 小時**；
- 2026-11-06 00:10（台灣）才被假設為驗收；
- 費率來源直到 2026-11-07 才被假設取得。

程式會輸出 47.5 小時與「價格事後取得」的標籤，**但不會將其認定為 47.5 小時有效自主研究，更不會認證為 48 小時長程能力。**

另有九次虛構任務嘗試，覆蓋不同付費路徑、跨日執行、成功與失敗，全部要求模型身份、現金紀錄及任務起迄時間對齊。

## 7. 可重現操作

使用 Python 3.11+，無外部 Python 依賴。

~~~bash
python -m unittest discover -s tests -v

# 2024 當年：嚴格模式不得使用 2026 年才收集的來源
python -m fsl_economics.timeaxis_cli audit-sources \
  --catalog data/verified_release_and_price_vintage_2026-11-07.json \
  --as-of 2024-05-13 --mode strict_known_at_time

# 同一歷史日，以明示「事後重建」的方式查當年官方發布紀錄
python -m fsl_economics.timeaxis_cli audit-sources \
  --catalog data/verified_release_and_price_vintage_2026-11-07.json \
  --as-of 2024-05-13 --mode retrospective_reconstruction

# 合成跨日任務，驗證完整 UTC 與台灣時區變換
python -m fsl_economics.timeaxis_cli audit-mission \
  --file tests/fixtures/mission_clock_synthetic_2026-11-07.json

# 九次合成跨模型嘗試，要求每次的真正起迄、最後結果及額度費率時間
python -m fsl_economics.timeaxis_cli audit-panel \
  --file tests/fixtures/time_anchored_task_panel_synthetic.json
~~~

每一份 CLI 輸出都會記錄：

- report_generated_at_utc：當次程式執行的 UTC 生成時間；
- report_generated_at_Asia_Taipei：同一時刻在台灣的時間；
- report_clock_source：實際依賴的軟體時鐘種類；
- as_of 或 cutoff_at：研究者主動指定的資料截止時間；
- 源頭日期與精度，不能私自升格為精確 UTC 發布秒數。

這些生成時間是 GitHub Runner 或執行機的系統時鐘，不是獨立可信時間簽章服務；對抗嚴格竄改還需外部服務時間收據。

## 8. 從時間資料到功能性 AI 的真實發展

在建立正確時間座標後，再將以下結果組合：

- 模型與工具實際公開時間，及其在當時是否具備完成任務的條件；
- 訂閱／API 的實際可用額度及其重置或政策變動日期；
- 同一任務獨立成功率與成果驗收時間；
- 真實人類介入時間、後續修正及長程狀態保持；
- 若歷史模型無法重跑，保存未知成功率／不可行狀態，禁止產生看似精確的美元倍率；
- 與 G1–G4/E1 不同階段的能力結果連結，才能研究不同能力何時以什麼成本變得可達。

真正的核心問題是：**同樣一個用戶真實目標，在 2024、2025、2026、2027 年，各自需要什麼模型、Agent、自主性、訂閱額度、時間與驗證代價，才能完成品質相同的成果？**

這個研究要能由日期與證據反駁，而不只是把當代的進步敘事倒灌回過去。
